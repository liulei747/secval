## 安全发现

### 1. 订单 API 对象级授权缺失：普通已认证用户可通过修改 order_id 读取任意用户订单（IDOR/BOLA）

- 严重性：`high`
- 置信度：`high`
- CWE：CWE-639, CWE-862
- 根因位置：`main.py:15`

#### 问题与影响

GET /orders/{order_id} 存在对象级授权缺失（IDOR/BOLA）：处理器以调用方完全可控的路径参数 order_id 直接索引内存订单表并返回完整对象（含 owner_user_id 与收货地址），request 参数声明但从未读取，代码中不存在任何用户身份与订单归属的比较；唯一边界 AuthMiddleware 仅检查 Authorization 头非空，不验证令牌、不提取或传递调用者身份。任意携带非空 Authorization 头的普通用户可通过修改 order_id 读取任意订单。

#### 根因

根因是订单读取路径上对象级归属授权缺失：get_order 以调用方可控的 order_id 直接索引订单存储（chunk 15-18 行窄范围），唯一集中边界 AuthMiddleware 仅做 Authorization 头存在性检查、不验证身份也不传递调用者上下文；数据模型中存在 owner_user_id 字段但从未参与访问判定，资源访问完全由攻击者可控的路径参数决定。

#### 攻击路径

普通已认证用户将 GET /orders/{order_id} 的路径参数替换为其他用户的订单 ID，请求穿过仅检查头存在性的 AuthMiddleware，处理器直接以该 ID 索引 ORDERS 并返回完整对象（含 owner_user_id、收货地址）。代码中不存在任何 user_id 与 owner_user_id 的比较，跨用户读取在应用层无任何阻拦。

#### 独立复核

证据支持IDOR/BOLA假设：订单读取路径上不存在有效的对象级归属授权控制。根因直接可见于完整源码：main.py:15-18 的 get_order 将调用方完全可控的路径参数 order_id 直接索引 ORDERS 并返回完整对象（含 owner_user_id 与收货地址），request 参数仅声明从未读取，全部快照代码中不存在任何用户身份与 owner_user_id 的比较，也没有 Depends/依赖注入或其他授权层。唯一集中边界 AuthMiddleware（auth.py:8-12，经 main.py:9 注册）仅检查 Authorization 头非空即放行，不验证令牌、不提取或传递调用者身份，更不执行对象级授权。数据模型含 owner_user_id 字段但从未参与访问判定。因此问题正向部分的答案是"否"：防护不有效，漏洞成立——快照内任意携带非空 Authorization 头的调用方（实际宽于"普通已认证用户"，因中间件不验证令牌内容）请求他人 order_id 即可读取全部字段。影响评级 high（跨用户 PII 只读泄露、快照内无写入口）与源码一致；likelihood high 需附加条件：利用要求已知或可猜测有效 order_id，样例数据 1001/1002 连续不证明真实 ID 可枚举。

#### 修复建议

在 get_order 中先经可信来源解析当前用户身份（网关注入的 user_id 必须经服务端验证而非直接采信），取回 ORDERS[order_id] 后校验 owner_user_id 与当前用户一致，不一致返回 404 或 403；同时让 AuthMiddleware 真正校验令牌并传递已验证身份；将归属校验集中到统一的授权层或服务方法，覆盖所有订单读取端点，避免逐路由遗漏。
