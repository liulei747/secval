# Secval 快速扫描与深度扫描设计

状态：设计提案，尚未实现。记录日期：2026-09-07。

本文定义 Secval 后续只读静态审计的两种扫描模式。设计参考 Codex Security 的标准扫描、
深度扫描和调查包方法，并吸收“Prefill-AI-Native-SAST”的批量端点初筛思路，但使用 Secval
自有的固定源码快照、OpenSearch、Qdrant、Neo4j、Joern、模型适配器和任务存储实现，
不声称复制任何外部产品的内部服务或性能结果。

## 1. 设计目标

1. 用户选择“快速”或“深度”，不再估算全队需要多少模型调用步数。
2. 并发槽位只控制同时运行的 Agent 数量，不限制整个扫描能创建多少个有界任务。
3. 主协调器先理解项目和攻击面，再按真实安全边界生成调查包，避免固定三个 Agent 平分预算。
4. 完成度由调查包、候选验证和覆盖状态决定，不由一个共享步数计数器决定。
5. 时间、token、费用、连续错误和单任务循环限制仍作为资源保护，不作为“审计完成”的证明。
6. 所有中间结果及时落盘；中断、超时和部分失败不得丢失已完成结果。
7. 将确定性的源码取证和上下文组装前移，减少 Agent 重复搜索、读取和长输出。
8. 批量模型只负责发现和排序候选，正式发现仍须经过源码回读、反证和独立验证。

## 2. 共同审计单元

两种模式都执行同一种完整扫描工作流，差别在于重复次数和聚合方式。

```text
固定仓库、快照和授权范围
  → 建立源码清单与能力清单
  → 协调器架构建模 + 生成 EndpointAuditPacket
  → 批量 Prefill 初筛并持久化短结构化结果
  → 独立基线审查 + 生成 InvestigationPacket 调查包
  → 动态派发专项调查 Agent
  → 协调器验证和反证每个唯一候选
  → 核对覆盖、延期项和证明缺口
  → 生成结构化报告
```

### 2.1 InvestigationPacket

调查包是任务拆解的核心，不直接按漏洞名称或文件数量平均切分。每个调查包至少保存：

- 稳定 `packet_id`；
- 攻击者及其初始能力；
- 受保护资产和预期安全约束；
- 入口、敏感操作和组件关系；
- 需要验证的具体控制；
- 可能获得的能力提升和必要前提；
- 固定快照中的源码锚点；
- 建议调查视角：正向、反向、授权/业务逻辑或开放调查；
- 优先级、依赖包、状态及延期原因。

相关问题共享攻击者、资产和控制时应合并；攻击边界、失效控制或修复方式不同则保持独立。

### 2.2 动态任务拆解

协调器负责：

1. 立即启动一个不继承协调器假设的独立基线 Agent。
2. 自己结合入口清单、类型关系、调用图、Spring 注入和 Joern 路径建立架构模型。
3. 有源码起点后生成调查包，不等待所有架构工作结束。
4. 根据调查包的独立性和复杂度派发专项 Agent；相关包复用同一个 Agent。
5. Agent 完成后继续从队列领取任务，总任务数不等于并发槽数。
6. 新证据可以新增、合并或重新打开调查包，但必须记录原因。
7. 协调器对每个去重候选独立验证一次，并保留最强反证和未知项。

子 Agent 只处理一个有界任务，不创建孙任务。专项结果只作为候选材料，不能直接成为正式发现。

### 2.3 覆盖与完成条件

以下条件全部满足时，单次完整扫描才可进入正常报告完成状态：

- 所有高优先级调查包已验证、被反证或明确延期；
- 所有候选均有唯一处置结果；
- 请求范围内的重要入口和敏感操作有处置；
- 已审文件、排除文件、未审文件和不支持文件分别统计；
- 报告明确列出配置、依赖、动态行为和证据缺口。

搜索命中、架构建模、读取文件以及“没有新发现”都不能单独证明完整覆盖。

### 2.4 EndpointAuditPacket 与批量初筛

`EndpointAuditPacket` 是面向入口的确定性模型输入，不等同于调查包。它由程序从同一固定快照和
已绑定索引生成，目标是让模型直接判断候选，而不是在 Agent 循环中从零查找上下文。每个包至少包含：

- 稳定 `endpoint_packet_id`、仓库、快照、批次、入口类型和源码锚点；
- 入口函数、参数、权限/框架注解及必要源码正文；
- Tree-sitter/Neo4j 提供的有界调用链、类型、继承、接口实现和 Spring 注入关系；
- Joern 提供的调用位置、控制流或数据流候选；
- OpenSearch/Qdrant 补充的实现线索及其来源标识；
- 经过安全边界感知裁剪的相关源码片段、缺失依赖和不确定关系。

上下文不机械限定为“入口加直接调用”或固定 4 KB。普通路径默认展开一至两层；遇到数据库、文件、
命令、模板、反序列化、网络请求等敏感操作时允许沿图继续展开到 sink；遇到鉴权、拦截器、AOP、
接口分派或注入时补充相关实现和配置。达到上下文上限后保留入口、敏感操作附近源码、关系摘要及
文件行号，并明确记录裁剪项，不能把裁剪后的未命中解释为安全。

初筛按模型供应商实际能力选择批处理 API、连续批处理、提示词缓存或受控并发；不得假设并发请求
天然共享 KV Cache。多个包可以合并为一批，但每个结果必须独立绑定 `endpoint_packet_id`。输出采用
严格 JSON Schema，并限制为候选发现所需的短字段，例如：

```json
{
  "result": "candidate",
  "category": "view_injection",
  "severity_hint": "medium",
  "entry": "DemoController.demo",
  "sink": "return viewName",
  "confidence": 0.78,
  "needs_agent_validation": true
}
```

初筛结果只允许为 `candidate`、`no_candidate`、`insufficient_context` 或 `invalid`。严重度和置信度均为
排序提示，不是最终结论。结构校验失败的单个结果可按策略重试一次，之后隔离失败，不拖垮整批任务。
高风险候选、上下文不足项和覆盖缺口进入调查包；阴性结果按安全边界和入口类型分层抽样复核。

## 3. 快速扫描

快速扫描对应一次完整、自适应的安全扫描，适合日常检查、首次摸底和单个组件审计。默认使用
“确定性备料 → 批量初筛 → Agent 集中验证”，而不是让 Agent 逐入口重复检索全仓。

### 3.1 执行方式

```text
QuickScanCoordinator
├─ 协调器架构/威胁建模与 EndpointAuditPacket 生成
├─ 1..N 个批量初筛 Worker（受模型和资源并发控制）
├─ 1 个独立基线 Agent
├─ 0..N 个动态验证 Agent（受 Agent 并发槽控制）
└─ 协调器统一验证、覆盖核对和报告
```

`agent_concurrency` 默认 3，表示协调器之外最多同时占用多少执行槽应由实现明确；界面必须显示
“总并发数”或“子 Agent 并发数”，不能继续使用含义模糊的 `parallel_agents`。

### 3.2 默认资源策略

建议初始默认值如下，实施时通过真实基准再校准：

| 项目 | 默认值 | 行为 |
| --- | ---: | --- |
| 总并发槽 | 4 | 只限制并发，不限制任务队列长度 |
| 扫描软时限 | 30 分钟 | 停止创建低优先级新包，优先验证和报告 |
| 扫描硬时限 | 60 分钟 | 停止未完成 Agent，保存部分结果并生成部分报告 |
| 单 Agent 连续无进展 | 3 轮 | 结束或重新分派该调查包 |
| 单 Agent 连续格式错误 | 3 次 | 标记该 Agent 失败，不终止其他任务 |
| 单 Agent 连续请求错误 | 3 次 | 熔断该 Agent，可按策略重新排队一次 |
| 单候选独立验证 | 1 次 | 证据变化后才允许重新验证 |
| 初筛单项格式重试 | 1 次 | 再失败则隔离为 `invalid` |
| 阴性分层复核率 | 5% | 高风险边界可单独提高，不作为固定充分值 |

token 和费用采用任务级软/硬预算：达到软预算后收敛，达到硬预算后停止。它们可以由管理员配置，
但普通用户界面默认不要求填写。当前 `max_steps` 从用户完成条件中移除，只保留为内部异常循环保险，
且不得由全队共享的小数值触发正常扫描提前终止。

### 3.3 终止状态

- `completed`：登记范围和调查包正常收口；不等于项目绝对安全。
- `partial`：时间、token、费用、模型故障或证据缺失导致部分覆盖。
- `failed`：没有形成可用范围或没有任何可恢复扫描结果。
- `cancelled`：用户取消；保留已完成结果。

## 4. 深度扫描

深度扫描运行多次彼此独立的快速扫描，通过重复发现降低单次模型随机性，最后统一聚合。各次运行
可以使用不同的安全视角或确定性分包顺序，但必须使用同一固定源码快照，且不能继承其他运行的模型结论。

```text
DeepScanCoordinator
├─ Quick Scan Run 1
├─ Quick Scan Run 2
├─ Quick Scan Run 3
├─ ...
└─ 去重、差异核对、必要复验和最终报告
```

每个运行都从相同固定源码快照、授权范围、安全策略和用户上下文开始，但不继承其他运行的
推测或对话。已完成运行的候选在协调器中按根因、入口、敏感操作和证据指纹去重。

### 4.1 默认资源策略

建议采用以下可配置项：

| 配置 | 建议默认值 | 含义 |
| --- | ---: | --- |
| `scan_workers` | 4 | 同时运行的独立快速扫描数 |
| `agent_concurrency_per_scan` | 3 | 每个快速扫描的子 Agent 并发额度 |
| `stop_after_no_new` | 4 | 连续完成且没有新唯一候选的运行数 |
| `stop_after_consecutive_errors` | 3 | 连续失败运行数，达到后熔断 |
| `max_scan_runs` | 40 | 最多启动的独立快速扫描数 |
| `max_time_hours` | 24 | 深度扫描总硬时限；允许管理员提高 |

深度扫描没有“必须跑满 40 次”的要求。满足 `stop_after_no_new` 后提前收敛；达到时间上限时取消
未完成运行，保留已完成结果并聚合为部分覆盖报告。如果没有任何运行完成源码审查，则不能生成
“未发现漏洞”的正常报告。

### 4.2 聚合与复验

聚合器应：

1. 使用稳定指纹合并同一失效控制，保留所有受影响入口和证据。
2. 不因多个运行重复报告而简单提高严重度或置信度。
3. 保存哪些运行支持、反驳或未能确认某候选。
4. 对运行间结论冲突的高风险候选安排一次独立差异复验。
5. 对覆盖取并集，但只统计各运行明确声明为完整安全审查的文件和安全面。
6. 报告连续无新发现次数、完成/失败/取消运行数及剩余证明缺口。

深度模式不得只重复同一个批量提示词。至少覆盖正向 source-to-sink、反向 sink-to-source、授权/业务
边界以及开放调查视角；初筛结果只用于扩大候选集合，冲突项和高风险项仍交给独立 Agent 复验。

## 5. Secval 证据工具的参与方式

- OpenSearch/Qdrant：寻找未知实现和语义相似线索，不作为漏洞证据本身。
- Neo4j：定位声明、调用、继承、动态分派、Spring Bean 和注入关系。
- Joern：提供调用位置、控制流和静态数据流候选。
- 固定源码快照：最终证据来源；所有图和搜索线索必须回读源码核实。

协调器生成调查包时应优先利用结构化入口与关系图，避免让每个 Agent 从全仓文本搜索重新开始。
不同 Agent 可以共享只读事实缓存，但不能共享未经验证的模型结论。

## 6. 状态与持久化

新增建议对象：

- `ScanTask`：模式、固定范围、策略版本、软/硬资源限额和总体状态。
- `ScanRun`：深度扫描中的一次独立快速扫描；快速模式只有一个 Run。
- `EndpointAuditPacket`：入口级确定性上下文、裁剪记录、索引来源和源码锚点。
- `PrefillBatch`：批次、模型参数、缓存/批处理能力、输入输出统计和失败隔离信息。
- `TriageDecision`：初筛状态、类别、严重度提示、置信度及是否需要 Agent 验证。
- `InvestigationPacket`：动态任务单元及状态迁移。
- `AgentAttempt`：一次执行尝试、模型请求统计、错误和检查点。
- `CandidateDecision`：支持、反证、未知、复验和去重信息。
- `ResourceUsage`：按扫描、运行、Agent、阶段统计请求、token、时间和估算费用。

所有模型请求开始前预占资源，结束后结算；进程异常时通过租约回收。Agent 结果、候选处置和覆盖变化
应增量落盘，不能等最终报告时一次保存。

## 7. API 与界面提案

创建扫描：

```json
{
  "mode": "quick",
  "repository_id": "jeesite-project-api",
  "snapshot_id": "jeesite-project-main",
  "scope_paths": ["modules/test"],
  "triage_enabled": true,
  "triage_concurrency": 4,
  "agent_concurrency": 4,
  "allow_remote_code": true
}
```

深度模式额外接受管理员级高级设置；普通界面只显示预设档位，不默认暴露几十个参数。

进度至少展示：

- 当前阶段和扫描模式；
- 运行、排队和已完成 Agent 数；
- 调查包总数及各状态数量；
- 端点审计包的生成、排队、初筛、失败和抽样复核数量；
- 待验证候选；
- 已审、延期、排除和不支持范围；
- 时间、token、费用的软/硬预算使用情况；
- 当前是否正在收敛，或因何进入部分报告。

旧接口的 `max_steps` 在兼容期仍可读取，但新任务不再把它作为主要用户输入。旧任务继续按旧语义运行，
不能静默改变历史任务或续跑链的预算解释。

## 8. 实施顺序

1. 先引入 `mode`、`ScanRun`、`InvestigationPacket` 和资源统计模型，不改变现有报告契约。
2. 将共享 `max_steps` 改为并发槽、软/硬预算和单 Agent 保险限制。
3. 实现 `EndpointAuditPacket` 生成器和严格短 JSON 初筛；先验证普通调用、危险 sink、鉴权边界、
   Spring 注入与接口分派的上下文裁剪。
4. 增加批处理/提示词缓存能力探测、受控并发、逐项结构校验、失败隔离和阶段级资源统计。
5. 重构快速扫描协调器：批量初筛、独立基线、动态调查包、阴性抽样和统一验证。
6. 用 JeeSite 单模块对比旧 Agent 流程与新混合流程的耗时、模型调用、token、候选召回和误报；
   不直接采用外部文章的“1 小时 1 万接口”作为验收指标。
7. 实现深度扫描协调器、不同视角的独立运行、无新发现收敛和聚合。
8. 用合成已知漏洞、无漏洞反例及 JeeSite 范围扫描评估召回、误报、资源和稳定性。

## 9. 明确不做

- 不把增加 Agent 数量当成提高审计质量的充分条件。
- 不按每个文件创建一个 Agent。
- 不把 Prefill 初筛结果直接提升为正式漏洞。
- 不因短上下文、模型 `temperature=0`、缓存命中或批处理成功而宣称结果可复现或覆盖完整。
- 不要求模型服务一定支持跨请求 KV Cache；不支持时退化为受控并发，且如实记录能力和成本。
- 不允许模型自行扩大授权范围或调整硬资源上限。
- 不因连续无新发现、工具无结果或深度扫描完成而宣称项目安全。
- 不在本阶段加入动态执行、Java Agent、自动利用或自动修复。
